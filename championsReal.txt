
Conventions:
  f_{w+2}, f_{omega+6}   braces always.  Unbraced, the '+2' looks like an addition
                         *outside* the subscript, and a level parser splits there.
  (f_{w+2})^114(9)       a superscript is an ITERATE COUNT in this file (the wiki's
                         '>fω22(4↑↑341)' means f_omega iterated 22 times), so it goes
                         outside parens.  Bare, it reads as an ordinal power sitting
                         in the index -- a whole Veblen level out.
  f_(omega^omega)(75500) but a superscript that is itself an ORDINAL is not an iterate
                         count at all.  (f_x)^n(a) is x folded n times on a, so at
                         n = omega there is no value to have: the folds are increasing
                         and each one is at least n, hence sup_n (f_omega)^n(a) = omega,
                         which is not a step count any halting run can have.  An ordinal
                         "iterate count" therefore names a LEVEL, and the level is the
                         diagonal taken over the index, not the composition:
                             sup_n f_{omega+n} = f_{omega*2}
                             sup_n f_{omega^n} = f_{omega^omega}
                         omega^omega is the second, so it goes inside the parens and is
                         spelled out.  Finite counts go outside as (f_x)^k; those are
                         literal folds and do have a value, so (f_omega)^22 is fine.
  f_(omega^2)(n)         an ordinal index, and also exactly what an ambiguous wiki
                         row writes when it means f_omega folded twice.  Default to
                         the fold (rank 10, still under f_{omega+1}); take the ordinal
                         (rank 17, above every f_{omega+k}, below f_{omega^omega})
                         only when the fold would put the row below a row at a
                         smaller (n,m), which monotonicity forbids.  ledger_audit.py
                         applies this and prints which reading it took.
  BB(n,m) is monotone in both n and m (pad a machine with unused states/symbols), so a
  row's level is never below a row at a smaller (n,m).  Rows below are per-machine
  analyses, not class optima; ledger_audit.py lists any that sit under an inherited bound.
